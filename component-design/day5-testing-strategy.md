# [Day 5] 프론트엔드 테스팅 전략: 단위 테스트부터 E2E까지

"테스트 코드는 시간 낭비다"라는 생각에서 벗어나, **"테스트 코드는 퇴근을 앞당기는 안전장치다"**라는 것을 체감하는 것이 오늘의 목표입니다. 오늘의 학습은 단순히 문법을 배우는 게 아니라, **"무엇을, 어디까지 테스트할 것인가?"**에 대한 전략적 판단 능력을 기르는 데 집중합니다.

---

## 1. 오늘의 핵심 개념 (Core Concepts)

### ① Testing Pyramid (테스트 피라미드)와 테스팅 치트시트

- **개념:** 비용이 저렴한 단위 테스트(Unit)는 많이, 비용이 비싼 E2E 테스트는 핵심 시나리오 위주로 구성하는 전략입니다.
- **Unit Test (Vitest/Jest):** 날짜 포맷팅, 금액 계산 등의 유틸리티 함수나 상태를 조작하는 순수 로직을 테스트합니다.
- **Integration Test (RTL):** 여러 컴포넌트가 협력하여 폼 입력 후 제출 버튼 클릭 시 성공 메시지가 노출되는지 등 특정 기능을 수행하는지 확인합니다.
- **E2E Test (Playwright/Cypress):** 로그인부터 결제까지, 실제 브라우저 환경에서 전체 비즈니스 흐름(Flow)이 끊기지 않는지 확인합니다.

### ② RTL(React Testing Library)과 사용자 중심 테스트

- **개념:** 컴포넌트 내부 구현(state, props)이 어떻게 변하는지가 아니라 **"사용자가 보는 화면"**과 사용자의 행동(클릭, 입력)에 집중합니다. 테스트가 소프트웨어가 사용되는 실제 방식과 유사할수록 더 큰 확신을 줄 수 있습니다.

### ③ Mocking과 MSW (Mock Service Worker)

- **개념:** 실제 서버 API를 호출하는 대신, 네트워크 레벨에서 가짜(Mock) 응답을 가로채어 테스트 환경을 격리하는 방법입니다,.
- **특징:** Service Worker API를 활용하므로 애플리케이션 코드를 변경할 필요가 없으며, 노드 환경(Jest, Vitest)과 브라우저 환경(Storybook) 양쪽에서 동일한 핸들러를 재사용할 수 있습니다,.

### ④ 테스트 커버리지의 함정 (Test Coverage Pitfalls)

- **개념:** 무조건 코드 커버리지 100%를 목표로 하는 것은 테스트 유지보수 비용만 낭비하는 안티 패턴입니다.
- **핵심 전략:** 장애가 났을 때 비즈니스 임팩트가 큰 **"결제", "인증", "핵심 유저 플로우"**에 테스트 리소스를 집중해야 합니다. 방어적인 테스트를 위한 테스트는 지양하세요.

---

## 2. 실무 SOP: 테스트 코드 작성 프로세스

- **① 엣지 케이스 정의:** 성공 케이스를 테스트하기 전에 **"데이터가 없을 때", "에러가 났을 때", "입력값이 잘못되었을 때"** 등의 예외 상황을 먼저 리스트업 하세요.
- **② AAA 패턴 활용:** 단위 테스트를 세 단계로 명확히 분리하여 가독성과 일관성을 높이는 표준 접근법입니다,.
  - **Arrange (준비):** 테스트에 필요한 환경, 데이터, 컴포넌트 렌더링 등을 준비합니다,.
  - **Act (실행):** 사용자의 행동(클릭, 타이핑)을 시뮬레이션하거나 대상 함수를 호출합니다,.
  - **Assert (검증):** 예상한 결과(메시지 노출, 함수 호출 등)가 올바르게 나타났는지 단언(Assertion)합니다,.
- **③ 접근성(Accessibility) 기반 쿼리:** 요소를 찾을 때 `getByTestId`를 남용하기보다는, 스크린 리더 등 사용자가 인지하는 방식과 동일한 `getByRole`, `getByLabelText`, `getByText`를 우선 사용하여 테스트 코드 자체가 웹 접근성 지표가 되게 하세요,.
- **④ Mocking은 최소한으로 (Identify Boundaries):** 내부 구현(Private 함수)이나 써드파티 라이브러리를 하나하나 Mocking하면 테스트가 깨지기 쉽고 신뢰도가 떨어집니다. MSW처럼 네트워크 경계에서만 모킹하고, 로직은 최대한 실제와 가깝게 두는 것이 유리합니다.
