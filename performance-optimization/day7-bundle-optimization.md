# day7 "당신의 번들이 너무 무겁다" — 현대 자바스크립트 성능을 뒤바꿀 5가지 반전 인사이트

현대 웹 애플리케이션의 복잡성이 기하급수적으로 증가하면서, 번들 최적화는 이제 선택이 아닌 엔지니어링의 '생존 전략'이 되었습니다.  
연구에 따르면 웹 페이지 로딩이 3초를 넘기는 순간 사용자의 40%가 이탈합니다.  
모바일 환경과 저대역폭 네트워크 사용자까지 고려한다면, 시니어 풀스택 엔지니어에게 가벼운 번들을 유지하는 것은 서비스의 가용성을 결정짓는 숙명과도 같습니다.

단순히 라이브러리를 추가하고 기능을 구현하는 단계를 넘어, "왜 이 기술이 필요한가"라는 전략적 관점에서 성능을 혁신할 수 있는 5가지 통찰을 공유합니다.

## 1. Moment.js의 시대는 끝났다: 0KB로 구현하는 국제화의 마법

한때 날짜 처리의 표준이었던 Moment.js는 이제 현대적인 웹 성능의 관점에서 기피 대상 1순위가 되었습니다.

> "Moment.js는 날짜 형식 지정 및 조작을 위한 가장 인기 있는 라이브러리였으나, 일부 사례에서 라이브러리의 크기와 구조적 문제로 인해 개발자들이 대안을 찾기 시작했습니다."

Moment.js의 가장 큰 결함은 트리 쉐이킹(Tree Shaking)이 불가능한 구조와 과도한 번들 사이즈입니다.  
시니어 엔지니어라면 추가 라이브러리 설치 없이 브라우저 내장 기능을 활용하는 `Intl API`에 주목해야 합니다.  
`Intl.DateTimeFormat`은 별도의 의존성 없이 로케일에 맞는 포맷팅을 제공하며, `Intl.RelativeTimeFormat`은 "3일 전"과 같은 상대적 시간 표현을 브라우저 수준에서 완벽하게 지원합니다.

더 나아가, 현재 Stage 3 단계인 `Temporal API`는 기존 `Date` 객체의 고질적인 문제였던 시간대(Timezone) 처리와 복잡한 날짜 연산(Date Arithmetic)을 해결할 미래의 표준입니다.  
이제는 무거운 라이브러리에 의존하기보다 웹 표준 API를 통해 번들 사이즈를 0KB로 유지하는 전략을 택해야 합니다.

## 2. '지연 로딩'을 넘어선 '예측 로딩': Webpack 매직 주석의 힘

`React.lazy`와 `Suspense`를 이용한 코드 분할(Code Splitting)은 이제 기본입니다.  
하지만 진정한 사용자 경험(UX)은 사용자가 클릭하기 전에 이미 준비되어 있어야 합니다.  
이때 강력한 도구가 되는 것이 **Webpack 매직 주석(Magic Comments)**입니다.

`/* webpackPrefetch: true */` 주석을 사용하면 브라우저는 CPU와 네트워크가 유휴 상태일 때 해당 청크를 미리 내려받아 캐시에 저장합니다.  
이는 사용자가 상호작용하는 순간 대기 시간을 '0'으로 만드는 마법을 부립니다.

- **경로 기반(Route-based) 분할**: 최적화의 가장 확실한 시작점입니다. 페이지 단위로 코드를 분할하여 초기 로딩 시 번들 사이즈 감소 폭을 극대화할 수 있습니다.
- **컴포넌트 기반(Component-based) 분할**: 모달, 텍스트 에디터와 같이 특정 상호작용 시에만 필요한 무거운 컴포넌트에 사용합니다. 이를 통해 보다 세밀한 성능 제어가 가능합니다.

전략적으로는 경로 기반 분할을 Mandatory(필수)로 적용하되, 사용자가 클릭할 확률이 높은 주요 기능(예: 랜딩 페이지의 로그인 모달)에 예측 로딩 기술을 결합하는 것이 최선입니다.

## 3. 82%의 기적: Lodash 임포트 방식 하나가 부른 대참사

무심코 작성한 Named Import 구문 하나가 번들 사이즈를 폭증시킬 수 있습니다. 대표적인 사례가 Lodash입니다.  
`import { cloneDeep } from 'lodash'`와 같이 임포트하면 번들러는 전체 라이브러리를 포함하게 됩니다.

| 임포트 방식                                | 번들 사이즈 | 비고                                     |
| ------------------------------------------ | ----------- | ---------------------------------------- |
| `import { cloneDeep } from 'lodash'`       | 547KB       | 전체 라이브러리 포함 (Tree Shaking 실패) |
| `import cloneDeep from 'lodash/cloneDeep'` | 97KB        | 약 82% 감소                              |

여기서 중요한 시니어급 인사이트는 **"왜 트리 쉐이킹이 작동하지 않는가"**입니다.  
Lodash의 메인 패키지는 CommonJS(CJS) 형식으로 작성되어 있어, 현대적인 번들러의 ES Modules(ESM) 기반 트리 쉐이킹이 정상적으로 동작하지 않기 때문입니다.

이러한 문제를 개발자의 주의력에만 맡기는 것은 위험합니다. `no-restricted-imports`와 같은 ESLint 규칙을 통해 시스템적으로 잘못된 패턴을 차단해야 합니다.  
"수동 코드 리뷰는 규모가 커지면 반드시 실패한다"는 점을 명심하고 자동화된 방지책을 마련하십시오.

## 4. 번들러의 혁명: Vite는 왜 Webpack보다 압도적으로 빠른가?

기존 Webpack의 개발 서버는 소스 코드 전체를 미리 번들링해야 하는 O(n)의 복잡도를 가집니다.  
프로젝트 규모가 커질수록 대기 시간이 기하급수적으로 늘어나는 구조입니다.

반면 Vite는 Native ESM 방식을 채택했습니다. 모든 모듈을 번들링하는 대신, 브라우저가 요청하는 모듈만 실시간으로 변환하여 전달하는 'On-demand' 방식을 사용합니다. 또한 의존성 사전 번들링에는 Go 언어로 작성된 초고속 엔진인 esbuild를 사용합니다.

하지만 기술 에반젤리스트로서 균형 잡힌 시각이 필요합니다.

- **Vite**: 현대적인 ESM 기반 프로젝트와 즉각적인 개발 피드백이 중요한 팀에 최적입니다.
- 향후 Rolldown이라는 통합 툴체인을 통해 개발과 프로덕션 환경의 일관성을 더욱 강화할 예정입니다.
- **Webpack**: 커스텀 로더 설정이 매우 복잡하거나, 레거시 시스템 지원이 필수적인 대형 엔터프라이즈 프로젝트에서는 여전히 유효하고 강력한 선택지입니다.

## 5. 트리 쉐이킹(Tree Shaking)의 함정: sideEffects를 잊지 마세요

트리 쉐이킹은 단순히 "안 쓰는 코드를 버리는 것"이 아닙니다. 번들러는 코드를 삭제했을 때 발생할 부작용을 극도로 경계합니다.  
이때 개발자가 `package.json`에 `"sideEffects": false` 설정을 추가하면, 번들러에게 "이 모듈들은 순수하므로 사용되지 않으면 과감히 삭제하라"는 강력한 힌트를 줄 수 있습니다.

여기서 주의할 점은 CSS 파일의 증발입니다. 단순히 `false`로 설정하면 트리 쉐이킹 과정에서 CSS 파일까지 삭제될 수 있습니다. 이를 방지하기 위해 다음과 같은 명시적 설정이 필요합니다.

```json
{
  "sideEffects": ["*.css", "*.scss"]
}
```

또한, 함수 호출 앞에 `/*#__PURE__*/` 주석을 다는 섬세함이 필요합니다.  
이는 **Terser와 같은 미니파이어(Minifier)**에게 해당 함수 호출이 사이드 이펙트가 없음을 알려, 정적 분석만으로는 판단하기 어려운 코드까지 안전하게 제거할 수 있도록 돕습니다.

## 결론: 더 가벼운 웹을 향한 끝없는 여정

성능 최적화는 단발성 이벤트가 아니라 지속적인 관측과 개선이 필요한 문화의 문제입니다.  
`rollup-plugin-visualizer`와 같은 도구를 CI/CD 파이프라인에 통합하여 번들 구조를 정기적으로 모니터링하십시오.

애플리케이션은 살아있는 나무와 같습니다.  
실제로 동작하는 코드는 초록색 잎이지만, 방치된 채 번들 사이즈만 키우는 죽은 코드(Dead Code)는 갈색으로 말라버린 잎과 같습니다.

"당신의 프로젝트 번들에서 지금 당장 덜어낼 수 있는 '죽은 잎'은 무엇입니까?"  
기술적 깊이를 더한 작은 습관이 사용자에게는 수 초의 쾌적함과 서비스의 신뢰로 돌아갈 것입니다.
