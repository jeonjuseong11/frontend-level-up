# Day 6 — JS 메모리 관리와 성능 최적화

## 1. 개요: 왜 내 웹사이트는 시간이 지날수록 무거워질까?

실시간 인터랙티브 애플리케이션(LMS의 라이브 클래스룸이나 WebRTC 기반 서비스)을 운영하다 보면 기이한 현상을 목격하곤 합니다.  
처음 접속했을 때는 쾌적하던 앱이 시간이 지날수록 채팅 입력이 밀리고, 페이지네이션 반응이 굼떠지며, 심지어 브라우저가 응답 없음 상태에 빠지기도 합니다.

대부분의 사용자는 이럴 때 '새로고침'으로 문제를 회피하지만, 이는 근본적인 해결책이 아닙니다.  
시니어 엔지니어의 시각에서 볼 때, 이러한 현상은 단순한 '속도'의 문제가 아니라 **메모리 관리(Memory Management)**의 실패를 알리는 경고등입니다.  
보이지 않는 곳에서 점진적으로 쌓인 메모리 부채가 결국 자바스크립트 엔진의 발목을 잡는 것이죠.

## 2. 핵심 1: 느려짐의 정체를 파악하라 — 메모리 이슈의 3가지 유형

성능 최적화의 첫걸음은 현상을 정밀하게 정의하는 것입니다.  
단순히 "느리다"는 모호한 진단 대신, Chrome Task Manager를 열어 다음의 세 가지 유형 중 어디에 해당하는지 확인해야 합니다.

- **Memory Leak (메모리 누수)**: 시간이 지남에 따라 점진적으로 페이지가 느려지는 현상입니다. 사용하지 않는 객체가 해제되지 않고 JS Heap에 계속 쌓일 때 발생합니다.
- **Memory Bloat (메모리 비대화)**: 처음부터 일관되게 많은 메모리를 점유하며 속도가 느린 상태입니다. 앱이 최적화된 설계보다 과도한 메모리를 기본적으로 사용하는 경우입니다.
- **Garbage Collection (GC) 과부하**: 화면이 뚝뚝 끊기는 스터터링(Stuttering) 현상입니다. GC가 너무 자주 실행되어 자바스크립트 실행이 빈번하게 중단될 때 발생합니다.

> 💡 **디버깅 팁**
> 디버깅 시 `Memory Footprint` 컬럼은 DOM 노드가 저장되는 '네이티브 메모리'를 나타내며, `Javascript Memory`의 `Live Number`는 현재 접근 가능한 객체들이 실제 점유 중인 'JS Heap'의 상태를 나타냅니다. 이 두 수치의 변화를 관찰하는 것이 디버깅의 시작입니다.

## 3. 핵심 2: 보이지 않는 유령, 'Detached DOM'의 습격

화면에서 요소를 제거했다고 해서 메모리에서도 완전히 사라진 것은 아닙니다.  
이것이 바로 **Detached DOM**입니다. DOM 트리에서는 떨어져 나갔지만, 자바스크립트 코드 어딘가에서 해당 노드를 여전히 참조하고 있다면 가비지 컬렉터는 이를 수거하지 못합니다.

실제 실무 사례로, `<SvgIcon />` 컴포넌트를 image sprite 방식으로 사용할 때 `<use>` 태그가 `SVGElement`를 계속 붙잡고 있어 누수가 발생하곤 합니다.  
이를 해결하기 위해 단순 참조 방식이 아닌, SVG를 inline 시킨 별도의 컴포넌트로 교체하는 기술적 판단이 필요합니다.

> "Detached elements aren't always an indication of a memory leak, and memory leaks aren't always caused by detached elements. Memory leaks depend on the context of your application."

🔍 **디버깅 시에는**  
Heap Snapshots의 Comparison 뷰에서 `detached` 키워드로 필터링하고, `Size Delta`를 기준으로 정렬하십시오.  
이를 통해 의도치 않게 메모리에 남은 유령 노드들을 정확히 찾아낼 수 있습니다.

## 4. 핵심 3: 애니메이션의 배신 — Lottie와 이벤트 리스너의 함정

화려한 인터랙션을 위해 사용하는 Lottie 라이브러리는 강력하지만, 관리하지 않으면 치명적인 '메모리 포식자'가 됩니다.  
Allocation Timeline 분석 결과, 상위 Retained Size(객체 해제 시 확보될 수 있는 메모리 총량)를 차지하는 주범이 `AnimationItem` 생성자인 경우가 많습니다.

특히 페이지네이션을 10회 수행하는 시나리오에서 적절한 클린업이 없을 경우, 메모리 할당량이 31MB까지 치솟기도 합니다.  
하지만 컴포넌트 언마운트 시 `.destroy()` 메서드를 명시적으로 호출하고, 등록된 `complete` 이벤트 리스너를 `removeEventListener`로 정리하면 할당량이 990KB로 급감합니다. **무려 96%의 성능 개선이 '지우는 코드 한 줄'에서 시작됩니다.**

## 5. 핵심 4: 브라우저의 우선순위 — Microtask와 Animation Frame의 질서

자바스크립트 엔진의 이벤트 루프는 비동기 작업을 처리할 때 엄격한 우선순위를 따릅니다.  
이 질서를 모르면 UI가 얼어붙는 현상을 막을 수 없습니다.

| 우선순위  | 큐 유형 (Queue Type)    | 주요 작업 예시                   | 특징                                             |
| :-------- | :---------------------- | :------------------------------- | :----------------------------------------------- |
| **1순위** | `Microtask Queue`       | `Promise.then`, `queueMicrotask` | 큐가 빌 때까지 엔진이 제어권을 놓지 않음         |
| **2순위** | `Animation Frame Queue` | `requestAnimationFrame (rAF)`    | 브라우저 리페인트(Paint) 직전에 실행             |
| **3순위** | `Macrotask Queue`       | `setTimeout`, `setInterval`      | 한 번에 하나의 태스크만 처리 후 렌더링 기회 제공 |

⚠️ 주의할 점은 **Microtask Queue**입니다.  
엔진은 이 큐가 완전히 비워질 때까지 다음 단계로 넘어가지 않습니다.  
만약 마이크로태스크가 계속 쌓이면 렌더링 직전에 실행되어야 할 rAF조차 실행되지 못하고 화면이 완전히 멈추는(Freeze) 현상이 발생합니다.

## 6. 핵심 5: 성능 최적화의 필살기 — 'rAF → setTimeout' 패턴

사용자 입력 반응성 지표인 **INP(Interaction to Next Paint)**를 개선하고 싶다면, 브라우저가 '숨을 쉴 틈'을 주어야 합니다.  
이때 활용하는 것이 `'rAF → setTimeout'` 패턴입니다.

`requestAnimationFrame(rAF)`은 리페인트 '직전'에 실행됩니다. 따라서 시각적 업데이트(예: 로딩 바 표시)를 즉시 처리하기에 최적입니다.  
하지만 그 직후에 이어지는 무거운 로직은 `setTimeout`으로 감싸 다음 프레임으로 넘겨야 합니다.

1. rAF를 통해 시각적 피드백을 사용자에게 보여줌 (Paint)
2. 다음 프레임(`setTimeout`)에서 무거운 로직 수행

결과적으로 **Presentation Delay(표시 지연)**가 감소하여 사용자는 앱이 자신의 입력에 즉각 반응한다고 느끼게 됩니다.

## 7. 결론: 지속 가능한 코드를 위한 개발자의 습관

성능 최적화는 '한 번의 이벤트'가 아니라 **'클린업의 습관'**입니다.  
시니어 엔지니어라면 코드를 짤 때 항상 다음의 도구들과 질문을 떠올려야 합니다.

- **Chrome Task Manager**: 현재 Memory Footprint와 Live Number의 추이가 정상인가?
- **Heap Snapshots & Comparison**: Size Delta가 큰 객체 중 Detached DOM이나 해제되지 않은 참조가 있는가?
- **Allocation Timeline**: 특정 액션 시 JS Heap 할당량이 비정상적으로 급증하지 않는가?

성능이 뛰어난 웹 앱은 단순히 코드를 잘 짜는 것을 넘어, 뒷정리를 완벽하게 하는 개발자의 손에서 탄생합니다.  
오늘 당신이 만든 컴포넌트는 떠날 때(Unmount) 자신의 흔적을 깨끗이 지우고 있나요? **"지우는 습관"**이 곧 최고의 최적화 전략입니다.
